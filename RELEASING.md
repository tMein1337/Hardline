# Releasing Hardline

Every binary release must be accompanied by the exact Corresponding Source for
that binary. That is an AGPL obligation, not a nicety, and it is the reason this
procedure is written down rather than improvised.

## Toolchain

Record the versions actually used, and put them in the release notes.

| Component | Version used |
|---|---|
| Flutter | 3.44.8 (stable) |
| Dart | 3.12.2 |
| Visual Studio | Community 2026, 18.8.2 - "Desktop development with C++" workload |
| MSVC toolset | 14.51.36231 |
| Windows SDK | as installed by the above |
| Target | Windows 10 1809 (x64) or later |

Read these off the machine that actually built the release rather than copying
them forward; 0.1.0 shipped claiming Visual Studio 2022 when it had in fact
been built with 2026, which would have sent anyone reproducing the build to the
wrong compiler.

Verify before building:

```sh
flutter --version
flutter doctor -v
```

## 1. Prepare

Release from a **clean checkout of a tagged commit**, never from a working tree
with local changes.

```sh
git status --porcelain          # must be empty
flutter pub get
flutter analyze                 # must be clean
flutter test                    # must be green
dart run tool/generate_third_party_notices.dart --check
dart run tool/check_dependency_advisories.dart   # needs network
```

The advisory check queries OSV for every package resolved in `pubspec.lock` and
exits non-zero on a hit. Do not tag a release without running it online — a
package can pick up an advisory without its version changing.

If the notices check fails, regenerate and commit before continuing:

```sh
dart run tool/generate_third_party_notices.dart
git add THIRD_PARTY_NOTICES.md && git commit -m "chore: refresh third-party notices"
```

## 2. Set the version

The version in `pubspec.yaml` is the single source of truth. It is read at build
time into the About screen by `tool/write_build_info.dart`.

```yaml
version: 0.1.0+1
```

## 3. Tag

```sh
git tag -a v0.1.0 -m "Hardline 0.1.0"
git push origin v0.1.0
```

**The tag must stay available for as long as the binary is downloadable.** Never
delete or move a release tag; if a release is withdrawn, withdraw the binary and
leave the tag.

## 4. Build

```sh
dart run tool/write_build_info.dart          # stamps version + commit
flutter build windows --release
```

`write_build_info.dart` rewrites `lib/core/build_info.dart`, which is tracked --
it is committed with placeholder values so that a fresh clone compiles without
running the tool first. This step therefore leaves the tree with exactly that
one file modified, by design, and the packaging script's clean-tree check
allows that file and nothing else. Do not commit the stamped values; put the
placeholders back once the release is packaged:

```sh
dart run tool/write_build_info.dart --reset
```

Output: `build\windows\x64\runner\Release\`.

That whole directory is the application. `hardline.exe` alone will not run — it
needs `flutter_windows.dll`, the plugin DLLs and `data\`, which includes
`icudtl.dat` and the compiled Dart. **Never publish the bare `.exe`.**

## 5. Package

```powershell
powershell -ExecutionPolicy Bypass -File tool\package_windows_release.ps1 `
  -Version 0.1.0 -Tag v0.1.0
```

This stages `dist\hardline-0.1.0-windows\` containing the complete runtime plus:

- `LICENSE`
- `THIRD_PARTY_NOTICES.md`
- `PRIVACY.md`
- `SOURCE.md` — with the version, tag and commit filled in
- `README.txt`

then zips it and writes `SHA256SUMS.txt`.

Confirm no placeholder survived:

```powershell
Select-String -Path dist\hardline-0.1.0-windows\SOURCE.md -Pattern 'PLACEHOLDER'
```

That must return nothing.

## 6. Sign

Authenticode-sign both the executable and the archive or installer, and
timestamp the signature so it stays valid after the certificate expires.

```powershell
signtool sign /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 `
  /f cert.pfx /p $env:CERT_PASSWORD `
  dist\hardline-0.1.0-windows\hardline.exe

signtool verify /pa /v dist\hardline-0.1.0-windows\hardline.exe
```

Options if you have no certificate: an OV/EV code-signing certificate from a
commercial CA, or a qualifying open-source signing service such as SignPath.
Re-run the checksum step after signing — signing changes the file.

> **Status for 0.1.0:** if the release is unsigned, say so plainly on the
> release page and tell users to expect a SmartScreen warning and to verify the
> published SHA-256 instead. Do not imply a signature that does not exist.

## 7. Checksums

```powershell
Get-FileHash dist\hardline-0.1.0-windows.zip -Algorithm SHA256 |
  Format-List
```

Publish the SHA-256 in the release notes, not only as an attached file.

## 8. Source release

Attach to the same release page:

1. `hardline-0.1.0-source.zip` — the tagged tree. Generated by GitHub
   automatically; verify it matches the tag.
2. Optionally `hardline-v0.1.0-dependencies.zip` — a copy of the pub cache for
   the exact `pubspec.lock`, so the build survives a package disappearing from
   pub.dev:

   ```sh
   dart run tool/bundle_dependency_sources.dart
   ```

3. A **Source code for this release** link, placed directly beside the binary
   download — not only a link to the repository's front page.

## 9. Verify before announcing

- [ ] Install on a **clean Windows machine** with no Flutter toolchain.
- [ ] The app starts, signs in, sends a message, and joins a call.
- [ ] **Settings → About** shows the right version and commit, and its source
      link resolves to this release's tag.
- [ ] The published SHA-256 matches the uploaded file.
- [ ] `LICENSE`, `THIRD_PARTY_NOTICES.md`, `PRIVACY.md` and `SOURCE.md` are all
      present in the package.
- [ ] Every checklist item in `RELEASE-LEGAL-ROADMAP.md` under **BLOCKERS** is
      green.

### The clean machine can be Windows Sandbox

Windows 11 Pro includes Windows Sandbox, which boots a fresh Windows image in
about twenty seconds and destroys it on close. That is a better clean machine
than a virtual machine you maintain, because it cannot be contaminated by an
earlier test run.

Enable it once, from an elevated PowerShell:

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All
```

Then save this as `clean-test.wsb`, correcting the host path, and double-click
it:

```xml
<Configuration>
  <MappedFolders>
    <MappedFolder>
      <HostFolder>C:\path\to\repo\dist</HostFolder>
      <SandboxFolder>C:\hardline</SandboxFolder>
      <ReadOnly>true</ReadOnly>
    </MappedFolder>
  </MappedFolders>
  <Networking>Enable</Networking>
  <vGPU>Enable</vGPU>
  <MemoryInMB>4096</MemoryInMB>
  <LogonCommand>
    <Command>powershell -NoProfile -WindowStyle Hidden -Command "try { Invoke-WebRequest -UseBasicParsing https://example.com | Out-Null } catch {}"</Command>
  </LogonCommand>
</Configuration>
```

The `LogonCommand` is the certificate-store warm-up described under the traps
below. `dist/clean-test.wsb` and `dist/hardline-clean-test.wsb` in this repo
are the same file with the host path already filled in.

Test **both** downloads. They are built from the same staged directory, but
they are two published artifacts and the installer exercises a different path
onto disk than the archive does.

Do not use Hyper-V Quick Create's "Windows 11 dev environment" image. It has
Visual Studio pre-installed, so the Visual C++ runtime is already present and
the test proves nothing.

**Two traps, both of which look exactly like real failures:**

- **A cold certificate store.** Windows fetches trusted roots on demand, and a
  freshly booted sandbox has almost none. The first HTTPS request can therefore
  fail TLS validation even though the network, DNS and the server are all fine.
  Making any other HTTPS request first — `Invoke-WebRequest https://example.com`
  — populates the store, after which sign-in works. No real machine hits this,
  because ordinary browsing fills the store long before anyone installs a Matrix
  client.

  **The `LogonCommand` above now does this on boot**, so it should not be
  reachable from a `.wsb` in this repo. It is described anyway because it is
  what a hand-written sandbox config will still hit, and because the shape of
  the failure is worth recognising: the app now says *"Reached that homeserver
  but could not verify its certificate"* rather than folding it in with a
  genuine network failure, so the two are told apart on sight.
- **Rendering.** Flutter draws through the GPU, so leave `vGPU` enabled. A blank
  or broken window is far more likely to be a sandbox limitation than a bug in
  the application.

Verified this way for 0.1.1: both the installer and the portable archive start
on a machine that has never had the Visual C++ Redistributable, which 0.1.0
could not do — it fails there with a missing `VCRUNTIME140_1.dll`.

## macOS

The macOS release build is made by `.github/workflows/macos.yml` on a
GitHub-hosted Mac, so that it comes from the same clean, documented toolchain
every time; a local build on a developer's Mac is for trying things out, not
for the release page. It runs on every pull request
and on every `v*` tag. Pushing the tag from step 3 is therefore all it takes:
the run's `hardline-macos` artifact holds `hardline-<version>-macos.dmg` and
`SHA256SUMS-macos.txt`, packaged by `tool/package_macos_release.sh` with the
same documents and the same clean-tree and stamp checks as the Windows script.
Attach both to the release page by hand.

The image contains `Hardline.app`, a universal binary (Apple silicon and
Intel), for macOS 10.15 or later.

Read the toolchain off the run's "Toolchain versions" step for the release
notes: Flutter, Xcode and Rust as the runner actually had them.

**Signing.** The build is ad-hoc signed only, not signed with a Developer ID
and not notarized. Gatekeeper refuses it on first open; `README.txt` in the
image explains "Open Anyway". Say so plainly on the release page, as for an
unsigned Windows build. Developer ID signing and notarization need an Apple
Developer Program membership and its certificate as repository secrets; until
then there is nothing to sign with.

**Not on macOS:** the game overlay and its global hotkeys are Windows-only
(`windows/runner/overlay_window.cpp` has no macOS counterpart), and the
settings pane says so. Screen sharing asks for the Screen Recording permission
in System Settings the first time.

## Nix release

There is no file to build or attach: Nix users build or fetch the package from
the tag itself (`github:tMein1337/hardline/<tag>`), and
`.github/workflows/nix.yml` builds every `v*` tag and pushes the result to the
Cachix cache.

The About screen's **Tag** line needs one extra commit. A flake never sees the
ref it was fetched by, only the commit, so the tag is read from
`nix/release.nix`, which is `null` on main. The tag points at a commit on top of
the release commit that sets it and changes nothing else; that commit is pushed
only as the tag and is **never merged into main**:

```sh
git switch --detach <release commit>
sed -i 's/  tag = null;/  tag = "v0.3.1";/' nix/release.nix
git commit -am "release: v0.3.1"
git tag -a v0.3.1 -m "Hardline 0.3.1"
git push origin v0.3.1
git switch main
```

The source of the release is that tagged commit, so it is the commit to name in
`SOURCE.md` and the release notes, and the commit the Windows and macOS builds
of the same tag are made from too (the extra line does not touch the app). CI
refuses a branch or pull request where `nix/release.nix` is not `null`, a tag
it names that is not the pushed one, and a `*-nixos` tag that it does not name.
A tag without the stamp still builds; its Nix package just says `unknown`.
The flake also refuses a tag that does not start with `v<pubspec version>`.

## 10. Keep it available

For as long as any binary of a version is downloadable:

- keep its tag,
- keep its source archive,
- keep its `THIRD_PARTY_NOTICES.md`.

Removing the source for an old binary while the binary is still offered is a
licence violation. If you must stop distributing a version, remove the **binary**
and leave the source.

## Notes

### The application data directory moves with the executable's identity

`getApplicationSupportDirectory()` on Windows resolves to
`%APPDATA%\<CompanyName>\<ProductName>`, taken from the `Runner.rc` version
resource. Changing either of those values moves the database, the media cache
and the preference store, and users appear signed out.

The rename from `com.example\matrix_client` to `Mein1337\Hardline` happened
before the first public release, so no released build is affected. Anyone with a
pre-release build can carry their session over by moving the old directory to
the new path while the app is closed. **Do not change these values again after
0.1.0 without shipping migration logic.**

The Matrix SDK client name and database filename are a separate identifier and
are deliberately left as `matrix_client`, because changing them would rename the
database file for no user-visible benefit.
